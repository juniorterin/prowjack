# The stream pipeline

**Question:** what actually happens between Stremio asking for streams and a video playing? This is the one flow that touches nearly every module in the project, so it's worth having mapped out before changing any one piece of it.

**Answer — `GET /:userConfig/stream/:type/:id.json`, `routes/stream.js`:**

1. `configStore.resolvePrefs(userConfig)` + `accessKeys.checkAccessKey(prefs, req)`. No valid key → responds `{ streams: [] }`, not an error — the addon degrades to catalog-only rather than exposing an error state to the end user (see `.claude/docs/auth.md`).
2. Result cache check: `rc.get(streamCacheKey)`, key includes `STREAM_CACHE_VERSION` from `constants.js` so a code change to the formatting/scoring logic can force a full cache bust just by bumping that string. Alongside it, an in-process `streamWaiters` Map de-dupes **concurrent** requests for the same cache key — if a search is already in flight for this exact `type/id`, a second incoming request awaits the same promise instead of starting a redundant search.
3. `jackettSearch.jackettSearch(plan, indexers, prefs)` queries every configured indexer in parallel. It handles Jackett (Torznab XML) and Prowlarr (native API) differently — `isProwlarrServer()` auto-detects and caches which one a given `JACKETT_URL`+key actually is, since despite the app's name/env vars, Prowlarr is now the recommended/primary target and Jackett is the legacy fallback. Per-indexer rate-limit state is tracked so a `429` from one indexer doesn't get hammered again immediately.
4. `scoring.js` is where results get ranked, filtered, and deduped: resolution/quality/codec/language regex tables score each release; `titleMatchScore`/`relaxedTitleMatchScore` compare the release title against the metadata title (from Cinemeta/Kitsu, via `jackettSearch.js`'s `getCinemetaTitle`/`getKitsuMeta`); for series/anime, `episodeMatchRank`/`animeEpisodeMatchRank` score how well a release's episode markers match the requested season/episode (exact `SxxExx` > declared range > season-only > season-agnostic complete pack > wrong episode); user prefs apply keyword-boost, priority-indexer, and exclusion filters on top.
5. `torrentUtils.js` resolves each surviving candidate's real BitTorrent infohash. Some results already carry one (`InfoHash`/magnet); others only have an HTTP download link, in which case the `.torrent` file itself gets downloaded and bencode-parsed to extract the real hash (a magnet's infohash from the query string can't always be trusted — some indexers wrap results behind a redirect or a generated magnet). `InfoHashQueue` caps how many of these downloads run concurrently; successes and failures are both cached in `rc` so a repeat search doesn't redo the work (see `.claude/docs/gotchas.md` for a real bug in this parser).
6. `scoring.formatStream(...)` renders the actual Stremio stream `name`/`description` — either the built-in emoji-heavy default format, or the user's custom `{token}` templates (`nameTemplate`/`descriptionTemplate` in prefs). Template rendering is line-oriented: a line that references only tokens which are empty for this particular result is dropped entirely (`renderTemplate`), so e.g. a user's `"🎧 {audio}"` line just vanishes for a release with no detected audio tag instead of printing a blank badge — this is why the token substitution isn't a simple global regex replace.
7. Crucially, the stream `url` returned to Stremio does **not** point at the torrent or at TorrServer directly — it's `/:userConfig/play/:jobToken`. The actual infohash/magnet/file selection is stashed under that short-lived token via `cache.savePlayJob(payload, ttl)`. This indirection exists so the potentially-slow "hand this to TorrServer and wait for its file listing" step (see below) only happens if and when the user actually presses play, not for every one of the (up to `maxResults`) streams shown in the picker.

## Playback — `GET /:userConfig/play/:jobToken`, `routes/play.js`

Re-checks the access key (the play link is a separate, unauthenticated-looking URL — it must re-gate, not just trust that the stream list was already gated), loads the job by token (`cache.loadPlayJob`), downloads and `torrentEnrich.injectTrackers()`s the `.torrent` if only an HTTP link was stored, then calls `providers/torrserver.resolvePlayTarget({ magnet, torrentBuffer, fileIdx, fileName })` — which adds the torrent to TorrServer, polls `waitForFileStats` until TorrServer has enumerated the torrent's files, and picks the right one (`pickTargetFile`, matching by index/name, falling back to the largest video file), returning `{ hash, fileId }`.

**Deliberately not a redirect.** `routes/play.js` used to `res.redirect(302, streamUrl)` straight to TorrServer's own `/play/:hash/:fileId` — but that means the player talks to TorrServer directly for the rest of the playback session, on a URL that (once known) needs no access key to reuse. Since TorrServer has no concept of this app's per-viewer access keys (`accessKeys.js`) — it only supports a single global `TS_USER`/`TS_PASS` basic-auth pair — the only way to actually gate playback by access key is for every byte to pass through this app. So `routes/play.js` instead calls `providers/torrserver.proxyStream(req, res, hash, fileId)`, which forwards the request (including `Range`/`If-Range` headers, so seeking still works) to TorrServer over the internal `TS_URL` and pipes the response straight back to the player — TorrServer itself never needs to be reachable from outside the Docker network/host. The trade-off is that video bytes now flow through this app's process instead of a direct player↔TorrServer connection, which is the necessary cost of the access-key check actually meaning something for the whole playback session, not just the first request.
